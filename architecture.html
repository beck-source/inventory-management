System Architecture — Reference Sheet

Factory Inventory Management System

A Vue 3 SPA talking to a stateless FastAPI service, backed entirely by JSON files read into memory at startup. No database, no auth, no persistence between restarts — built for a Claude Code workshop, not production.

Frontend
Vue 3 + Vite · :3000
Backend
FastAPI + Uvicorn · :8001
Data store
7 JSON files, in-memory
Persistence
None — resets on restart
01

System overview

three tiers, one process each

The browser and the API are two separate dev servers talking over plain HTTP; the API has no tier behind it beyond the Python process's own memory. mock_data.py reads all seven JSON files once, at import time — every request afterward filters that same in-memory list, and nothing ever writes back to disk.

Nothing survives a restart

Any POST/PATCH/DELETE the API accepts mutates the in-memory Python list for that process only. Restarting main.py reloads straight from server/data/*.json and silently discards it.

02

Filter → request → render

how one filter change reaches the screen

All four global filters — Time Period, Warehouse, Category, Order Status — live in one place: useFilters.js holds them as module-level ref()s, so every component that calls useFilters() shares the same four values rather than getting its own copy. Changing a dropdown in FilterBar.vue is therefore visible to every view simultaneously.

03

Frontend composition

client/src — one shell, six routed views

main.js mounts a single App.vue shell that never unmounts; router-view is the only part that swaps as the six top-level routes change. Three views open a detail modal on row-click, which fetches its own record rather than reusing the list already in memory.

Frontend/backend drift

client/src/api.js also calls /api/tasks (GET/POST/DELETE/PATCH) and /api/purchase-orders (GET/POST) — but neither exists in server/main.py. App.vue's loadTasks() catches the failure silently and falls back to useAuth.js's hardcoded mock tasks, which is why the Tasks modal still appears to work. Anything that calls createPurchaseOrder from the Backlog view will surface a real 404.
