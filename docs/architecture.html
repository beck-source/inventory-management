Notable Design Decisions
Restocking write path — done properly
Good
Frontend — Restocking.vue, api.js Backend — main.py Tests — test_restocking.py
The new_features branch adds a real write endpoint. POST /api/restocking-orders takes a Pydantic CreateRestockingOrderRequest, validates it (empty order and non-positive quantities both return 400), computes per-line and order totals, derives lead time from the slowest item category, stamps an expected delivery date, returns 201, and persists to an in-memory restocking_orders[] store — plus backend tests. Runtime-only state is consistent with the app's in-memory approach. This is the reference pattern the remaining stubbed writes should follow.
In-memory data, no database
Defensible
Backend — mock_data.py Data — server/data/*.json
All JSON files load into Python module-level lists at startup; filtering runs in-memory. Zero setup friction — no DB credentials, no migrations, no seed scripts. Right call for a demo or workshop. The cost: no persistence, restarts wipe any writes, and the data cap (~10K items) is baked in. Acceptable tradeoff until a real database is needed.
Write endpoints called but not implemented
Partial
Frontend — api.js, TasksModal.vue Backend — main.py
Originally, every write called from the frontend 404'd silently — the UI looked functional but writes failed invisibly. The new_features branch closes part of this gap: the restocking write path is now fully implemented and tested (see above).
✓ Addressed: restocking submission — POST /api/restocking-orders is real, validated, and returns 201.
✗ Still open: POST /api/tasks, DELETE /api/tasks/{id}, PATCH /api/tasks/{id}, and POST /api/purchase-orders still have no routes in main.py and 404 silently. Implement them following the restocking pattern, or disable the UI actions so the behavior is honest.
useFilters.js singleton pattern
Defensible
Frontend — composables/useFilters.js Frontend — FilterBar.vue, all views
Four ref() values declared at module scope (outside the composable function) make filter state truly global without Pinia or Vuex. FilterBar writes; every view watches and re-fetches. Clean for this scale and avoids a state-management dependency. The tradeoff: module-level mutation is hard to unit-test, can't scope filters per page, and the pattern silently diverges from standard composable conventions — could mislead newcomers.
Mixed filtering strategies across views
Bad
Full stack — filter path varies by view Frontend — Spending.vue, Demand.vue, Restocking.vue Backend — apply_filters()
Multiple filtering strategies coexist with no documentation: Inventory/Orders/Dashboard filter API-side; Spending pre-loads everything and filters client-side via computed properties (so warehouse/category changes do not trigger a re-fetch); Demand and Backlog filter client-side by SKU intersection. The result is a UX inconsistency — changing the Location filter visibly affects some views but silently does nothing on others.
✗ Still open — slightly extended: the new Restocking view adds a fourth pattern — it ignores the warehouse/category filters entirely, re-ranks on a budget slider, and reads selectedLocation only at order-submit time. A single, documented strategy would still be far easier to reason about.
Reports.vue: Options API outlier
Bad
Frontend — views/Reports.vue Frontend — api.js (bypassed)
The only view not using Composition API. It calls axios directly instead of going through api.js, has no filter integration (warehouse/category/period selections are ignored), and uses var instead of const/let. This looks like it was written separately and never brought in line with the rest of the codebase.
✗ Still open: untouched by new_features. The newly added Restocking.vue follows the standard setup() + api.js + composables pattern correctly, which only makes Reports.vue stand out further as the lone outlier. Migrating it to Composition API + api.js remains outstanding.
i18n built in; hardcoded exchange rate
Defensible
Frontend — composables/useI18n.js Frontend — utils/currency.js
Full EN/JA localization via a singleton composable is a good pattern — product names, warehouse names, user names, and currency all localize correctly. The defensible part: rolling a custom i18n engine instead of using vue-i18n means more surface area to maintain. The bad part within it: the JPY/USD exchange rate is hardcoded at 150:1 in currency.js. Exchange rates move; this will silently display wrong numbers. A constant named HARDCODED_EXCHANGE_RATE (or a config value) would at least make the brittleness visible.
✓ Reinforced: the entire restocking feature is fully bilingual — en.js and ja.js both gained the new strings, and Orders/Restocking use t() throughout.
✗ Still open: restocking amounts are formatted with a hardcoded currency: 'USD' (formatCurrency/formatUsd), bypassing the JPY conversion entirely — a new seam alongside the still-hardcoded exchange rate.
