Data Flow

What happens when a user changes a filter (for example, Warehouse = "San Francisco", Period = "Q2").

Filter changeFilterBar updates shared refs in useFilters. Every view sees the same state.
Build requestgetCurrentFilters() maps the period to month. api.js leaves out any filter set to "all".
HTTP GETe.g. /api/orders?warehouse=...&month=Q2
In-memory filterapply_filters() then filter_by_month() (quarters expand to their months) run over the Python lists.
Validate and returnPydantic response_model checks the shape, then FastAPI serializes it to JSON.
RenderViews store raw data in refs. KPIs, tables, and SVG charts come from computed properties.

Design Notes

Conventions and limits to know before you change the code.

Conventions

  • Raw API data lives in refs (allOrders, inventoryItems). Anything derived lives in computed properties.
  • Filter state is a module-level singleton, so it persists across route changes.
  • When a JSON data shape changes, update the matching Pydantic model in main.py.
  • Use stable keys in v-for (sku, month), never the index.
  • UI palette: slate/gray with green/blue/yellow/red for status. No emojis.

Limits (demo scope)

  • No persistence. Data reloads from JSON on every server restart.
  • Inventory has no time dimension, so the month filter does not apply to it.
  • Authentication is mocked in useAuth. The API has no auth.
  • CORS allows all origins and main.py binds to 0.0.0.0. Fine for local use only.
  • The API base URL is hardcoded in client/src/api.js.
