Factory Inventory Management System

Architecture overview: system layout, tech stack, and data flow

System Architecture

A two-tier demo application. There is no database; the API loads JSON files into memory at startup.

Browser - Vue 3 SPA - localhost:3000

Frontend (client/)

  • App.vue shell: top navigation, FilterBar, and a router-view
  • 6 routed views: Dashboard, Inventory, Orders, Spending, Demand, Reports (plus an unrouted Backlog.vue)
  • Shared state in composables: filters, auth (mock user), i18n (English and Japanese)
  • All HTTP calls go through src/api.js (axios), except Reports.vue, which calls axios directly

Backend (server/main.py)

  • FastAPI app with Pydantic response_model validation on most list and detail endpoints
  • Shared helpers apply_filters() and filter_by_month() (supports months and quarters such as Q1-2025)
  • Report endpoints aggregate orders by quarter and by month on each request
  • Auto-generated API docs at /docs

Data Flow

How a filter change on the Dashboard or Orders view reaches the screen.

  1. User changes a filter in FilterBar Writes to singleton refs in composables/useFilters.js: period, location, category, status.
  2. View reads the filters and calls the API client getCurrentFilters() maps them to warehouse, category, status, and month. Values equal to 'all' are omitted from the query string.
  3. Axios sends a GET request to http://localhost:8001/api/... Defined in client/src/api.js.
  4. FastAPI route filters the in-memory lists apply_filters() then filter_by_month(). Matching is exact for warehouse and case-insensitive for category and status.
  5. Pydantic validates the response Routes with a response_model serialize through it. The dashboard summary and spending routes return plain dicts.
  6. View stores raw JSON in refs For example allOrders and inventoryItems.
  7. Computed properties derive what is displayed Totals, chart series, and table rows recalculate from the refs.

Gaps Found in the Code

  • api.js calls /api/tasks (GET, POST, PATCH, DELETE) and /api/purchase-orders (POST, GET). No such routes exist in server/main.py, so those calls will return 404.
  • main.py defines PurchaseOrder and CreatePurchaseOrderRequest models, but no route uses CreatePurchaseOrderRequest.
  • The API has no authentication, and CORS allows all origins. The user profile is mock data in useAuth.js. This is suitable for local demo use only.
